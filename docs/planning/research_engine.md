## RECOMMENDATION
Use rclone (MIT, v1.75.0 2026-07-31) as the transfer engine, run as a GUI-managed local subprocess: spawn `rclone rcd` on a random localhost port with generated credentials, and have the GUI speak the JSON rc API (operations/list for browsing, _async sync/copyfile jobs for the queue, core/stats + _group for per-transfer progress, job/stop + core/bwlimit for control). This delivers, for near-zero engine code: concurrent multi-file transfers (--transfers), heavily pipelined SFTP (64 outstanding requests/file, chunk_size up to ~255K — tune these defaults up), non-blocking remote browsing during transfers (independent rc calls/connections — the CuteFTP fix), FTPS/WebDAV/S3/70+ backends for the "faster secure option" cases, dynamic bandwidth limiting, and trivial Ubuntu→Windows-x64 cross-compilation (pure-Go rclone.exe, CGO off). Prefer the rcd subprocess over librclone DLL: identical API, but no mingw-w64 cgo cross-compile pain, crash isolation, free choice of GUI stack, and independently upgradeable engine; switching to in-process librclone later is cheap since the call surface is identical (exception: if the GUI is written in Go, import rclone packages directly in-process). Plan custom work for the two known gaps: (1) SFTP has no multi-connection-per-file in rclone (issue #8185 open) — mitigation path is tuned single-connection pipelining first, then either contribute chunked multi-connection SFTP upstream or add an mscp-style fast path for huge single files (mscp proves this works against stock sshd, resume-checkpointing included); (2) rclone cannot byte-resume an interrupted single file and has no per-transfer pause — implement queue pause as job/stop + requeue (directory-level resume is inherent via sync semantics) and treat byte-level resume as a later custom feature. Reject WinSCPnet (subprocess scripting of the slow app, GPL exe) and FileZilla (GPL, engine not extractable). When the user controls the remote, expose an S3-compatible (MinIO) profile through the same rclone API — it is the fastest secure mechanism available (full multi-thread-streams, multipart resume) with zero extra engine code.

## FINDINGS
CONTEXT: All versions/dates verified current as of 2026-08-01 unless noted.

== 1. RCLONE AS EMBEDDED ENGINE ==
- Current version: v1.75.0 released 2026-07-31 (very active project). License: MIT — no copyleft obligations, safe to embed in closed or open GUI.
- Two embedding modes:
  (a) librclone: build with `go build --buildmode=c-shared -o librclone.dll` (or .a for static). Generates librclone.h. API surface is tiny: RcloneInitialize / RcloneFinalize / RcloneRPC(method, jsonIn) -> jsonOut / RcloneFreeString. RcloneRPC exposes the ENTIRE rc API in-process (same endpoints as the HTTP rc). Caveats: cgo-based, must never unload the DLL (Go runtime cannot unload), one Go runtime per process, callbacks/progress require polling core/stats via RPC. Cross-compiling a Windows c-shared DLL from Ubuntu requires mingw-w64 (CC=x86_64-w64-mingw32-gcc) — works but is the fiddliest part; a plain rclone.exe cross-build (GOOS=windows GOARCH=amd64, CGO off) is trivial.
  (b) `rclone rcd`: localhost JSON-over-HTTP daemon (default port 5572, use --rc-user/--rc-pass or --rc-auth; supports websockets for some ops, serves optional web GUI). Every operation is an endpoint: operations/list (directory browsing), operations/copyfile, sync/copy, core/stats (global + per-transfer bytes/speed/eta), core/bwlimit (dynamic rate limit change at runtime), job/list, job/status, job/stop, config/create, vfs/* etc. `_async=true` turns any call into a background job with a jobid; `_group` lets you track stats per job — this is exactly the primitive needed for a transfer queue.
- Concurrency: --transfers N (default 4) = parallel files; --multi-thread-streams N (default 4, cutoff 256Mi) = multiple streams per file. IMPORTANT GAP: multi-thread (multi-stream single-file) works for backends supporting ranged reads/OpenChunkWriter (S3, HTTP, local, most cloud); for SFTP it is NOT implemented — GitHub issue #8185 (opened 2024-11-16, still open) requests multi-connection SFTP à la mscp. However the SFTP backend gets substantial single-connection parallelism via SFTP request pipelining (see below).
- SFTP backend tuning knobs (rclone.org/sftp): --sftp-concurrency (default 64 outstanding requests per file), --sftp-chunk-size (default 32Ki, up to ~255Ki with servers that allow it — OpenSSH allows 256KB total packet), --sftp-connections (max simultaneous connections, 0=unlimited; rclone opens extra connections as needed for concurrent operations), disable_concurrent_reads / disable_concurrent_writes (both false by default — i.e., pipelined concurrent reads/writes are ON by default and rclone re-enabled concurrent writes specifically to fix a performance regression, commit 0537791), custom ciphers list (can pick aes128-gcm etc.), remote hash commands support. 64 requests x 32K = 2MB in flight per file; raising chunk-size to 255K gives ~16MB in flight — enough to saturate 1 Gbps at <120ms RTT on a single connection.
- Browsing while transferring: rc calls are fully concurrent; operations/list runs on its own SFTP connection while sync jobs run — this directly solves the CuteFTP blocking problem. No VFS/mount needed for browsing (VFS + WinFSP mount is available but unnecessary and adds fragility).
- Pause/resume: rclone has NO native per-transfer pause and NO resume of a partially transferred single file after interruption (long-standing limitation; forum threads through 2025 confirm; partial files are deleted/restarted). Mitigations: queue-level pause = stop submitting + job/stop running jobs; directory-level resume is inherent (sync/copy skips already-transferred files via size/modtime/hash); --partial/--inplace control temp-file naming. True byte-level resume of a huge single file would need custom work (or the mscp approach).
- Protocol breadth: 70+ backends — SFTP, FTP/FTPS (with --ftp-concurrency), WebDAV/HTTPS, S3-compatible, SMB, HTTP, crypt overlay, etc. — all behind one API.
- Existing GUIs embedding rclone (proof of viability): RcloneView (proprietary Windows/macOS GUI, drives rclone via rc API), Rclone UI (rcloneui.com, Tauri desktop app spawning rcd), official rclone-webui-react (served by `rclone rcd --rc-web-gui`), rclone-rc-web-gui (two-panel commander-style over rcd), H4R1B0/rclone-gui (macOS, librclone), trevyn/librclone (Rust bindings that auto-compile and link librclone). Pattern is overwhelmingly "spawn rcd, talk HTTP JSON".

== 2. NATIVE SFTP LIBRARIES ==
- SFTP protocol ceiling: throughput = (outstanding_requests x packet_size) / RTT, bounded by SSH channel window. Naive implementations (1 request at a time, 32KB packets) collapse on latency; pipelined implementations approach TCP speed. Single SSH connection is ultimately bounded by single-stream TCP + cipher throughput on one core (AES-NI GCM = multiple Gbps, rarely the bottleneck on 1 Gbps links).
- libssh2 (BSD-3, C): historically slow (11 Mb/s vs OpenSSH 80 Mb/s single-thread in old tests); pipelining work gave 8x gains; 1.11.x (1.11.0 May 2023, 1.11.1 Oct 2024) raised SFTP packet sizes and buffering — now competitive but you still hand-roll read-ahead/write-behind and one session is single-threaded (no thread-safe concurrent use of one session).
- libssh (LGPL-2.1 with static-link caveats, C): has async SFTP AIO API (multiple outstanding requests); mscp needed a patched libssh to get async SFTP *write* (patch derived from a libssh2 fork technique); newer libssh 0.11.x added an official sftp_aio API. Used by mscp successfully for multi-connection transfers.
- SSH.NET (MIT, C#): latest 2025.1.0 on NuGet; "optimized for parallelism", active releases 2024.0–2025.1 with real perf work; does internal read-ahead buffering; fine for a C#/WPF app but per-file multi-stream and connection pooling are DIY; historically slower than native/Go stacks for bulk transfer.
- golang.org/x/crypto/ssh + github.com/pkg/sftp (BSD): this is what rclone uses. pkg/sftp has UseConcurrentReads (default ON), UseConcurrentWrites, MaxConcurrentRequestsPerFile (e.g., 64) — genuine per-file request pipelining, saturates Gigabit easily. Best supported Go option; trivially cross-compiles Linux→Windows.
- Rust: russh (Apache-2.0, active, pure Rust, tokio-based) + russh-sftp (separate crate, younger/less complete); ssh2 crate = libssh2 bindings (inherits its session-level constraints). Workable but most custom code of any option.
- Verdict within this category: Go stack (x/crypto/ssh + pkg/sftp) has the best concurrency support out of the box — and rclone already wraps it with tuning, retries, and multi-backend support.

== 3. FASTER-THAN-SFTP SECURE OPTIONS ==
Split by whether the user controls the remote server:
REMOTE IS A STANDARD SSH/FTP SERVER (user does NOT control it) — realistic options:
- Multi-connection SFTP: open N SSH connections, split large files into chunks by offset, transfer chunks in parallel. Works against ANY stock sshd with the sftp subsystem — nothing needed server-side. Proven by mscp (upa/mscp, libssh-based, threads = CPU cores by default, chunk checkpointing for resume, PEARC'23 paper) and by rclone's per-connection request pipelining. This is THE practical speed play. rclone gives multi-file parallelism today (--transfers) but not multi-connection-per-file for SFTP (issue #8185).
- Pipelined single-connection SFTP with big chunks (rclone sftp-concurrency/chunk-size): often already saturates links up to moderate RTT; cheapest win.
- FTPS: raw TLS streams, no SFTP packet overhead, multiple data connections natively; fast; only if the server offers FTPS (rclone supports it incl. concurrency settings).
- rsync-over-ssh: requires rsync binary on the remote; single stream; delta-transfer is its win, not raw throughput; awkward on Windows client. Not a GUI engine candidate.
- HPN-SSH (rapier1/hpn-ssh, active, v15.x, PSC): dynamic TCP-matched SSH windows, threaded ciphers, optional NONE cipher (30%+ gains); BUT needs HPN on the SERVER for the big wins — irrelevant against servers the user doesn't control.
USER CONTROLS BOTH ENDS — additional options:
- S3-compatible endpoint (MinIO/Garage on the server) + rclone S3 backend: HTTPS, massively parallel multipart up/down, multi-thread-streams fully supported, checksums, resumable multipart uploads. Easily the fastest secure mechanism rclone offers; near line-rate on 10 Gbps.
- WebDAV over HTTPS: parallel range requests, decent; weaker semantics than S3.
- QUIC-based: SSH3 (francoismichel/ssh3, SSH over HTTP/3/QUIC) is v0.1.4 experimental, IETF draft stage, needs its own server — not production 2026. croc (schollz) / magic-wormhole: relay + PAKE, both ends run the tool, ad-hoc P2P sends — wrong model for a client↔server FTP replacement. No mainstream QUIC file-transfer protocol is deployable against servers you don't control in 2026.

== 4. WINSCP / FILEZILLA AS COMPONENTS ==
- WinSCP: app is GPL-3+. The .NET assembly (WinSCPnet) is MPL-licensed but is only a thin wrapper that SPAWNS winscp.com as a subprocess and scripts it — one blocking operation per session object, no per-file multi-stream, no real event-driven engine; you'd inherit the same performance profile the user is leaving. Poor fit as a high-concurrency engine; also drags GPL winscp.exe alongside.
- FileZilla: GPL-2+. libfilezilla is a generic C++ utility library (event loops, sockets, TLS wrappers), NOT the transfer engine; the actual FTP/SFTP engine lives inside the client (SFTP via a PuTTY-derived fzsftp helper process) and is not packaged for reuse. Embedding means writing a GPL app and vendoring a codebase not designed as a library. FileZilla also does not do multi-stream-per-file. Not recommended.

== KEY ARCHITECTURAL FACTS FOR SYNTHESIS ==
- rclone rcd subprocess model: GUI in any language; spawn `rclone rcd --rc-addr 127.0.0.1:PORT --rc-user u --rc-pass p` (random port + credentials); crash isolation (engine crash doesn't kill GUI); rclone binary upgradeable independently; identical API to librclone so switching to in-process later is cheap. Progress via polling core/stats (~250–500ms) or per-job _group stats.
- librclone DLL model: no subprocess management, single deliverable; but mingw-w64 cross-compile complexity, no unload, Go runtime pinned in-process, and still poll-based progress. Only worth it if shipping a Go GUI (then just import rclone packages directly — no cgo at all).
- Gaps to plan custom code for regardless of engine: (1) per-file multi-connection SFTP (contribute to rclone #8185, or shell out to mscp for huge single files, or accept pipelined single-connection speeds), (2) byte-level resume of interrupted single files on SFTP, (3) queue persistence/ordering/pause semantics (app-side state machine issuing _async jobs).

- Native C/C++/.NET/Rust SFTP stacks (libssh2 1.11.x / libssh 0.11 / SSH.NET 2025.1.0 / russh) [BSD-3 (libssh2), LGPL-2.1 (libssh), MIT (SSH.NET), Apache-2.0 (russh), Libraries mature (libssh2/libssh/SSH.NET); russh-sftp younger; engine on top is fully custom]: PROS: In-process, native to whatever GUI stack is chosen (SSH.NET fits a C#/WPF/WinUI app naturally); libssh2 1.11.x and libssh AIO now support large packets/pipelining; mscp proves libssh can do fast multi-connection transfers CONS: SFTP only — no FTPS/WebDAV/S3 breadth without more libraries; Pipelining, connection pooling, multi-stream, queue, resume all hand-rolled; libssh2 sessions not usable concurrently across threads; SSH.NET historically slower than Go/native stacks for bulk throughput; libssh LGPL complicates static linking; Highest risk of re-creating exactly the WinSCP-slowness problem being escaped
