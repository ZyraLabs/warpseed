## RECOMMENDATION
RANKED TOP-3: (1) Wails — the only framework where the GUI backend and the engine are the same Go process: rclone imported as a library gives zero-IPC progress callbacks, one binary, and the single best Linux->Windows cross-compile story of all nine (no CGO for the Windows target, plain GOOS=windows from the Ubuntu dev box). Web frontend gives solved virtualized lists and full freedom for a polished, non-generic Fluent-2-styled UI, and WebView2 process isolation guarantees browse-while-transferring responsiveness. Practical plan: start on Wails v2.12 (stable) with an eye on v3 GA, or accept v3 alpha-tracking since production apps already ship on it. (2) Tauri 2.x — pick this if the team prefers Rust or wants to lean on existing prior art: rclone-ui and RClone Manager prove the exact Tauri + `rclone rcd` sidecar architecture in shipping apps; cargo-xwin + NSIS cross-builds from Linux work in CI today, at the cost of a second language, a sidecar process, and HTTP-polled progress. (3) Avalonia 11/12 — the best answer if webview-based UI is rejected: real widget toolkit with TreeDataGrid (ideal dual-pane file-manager control), first-class `dotnet publish -r win-x64` from Linux, NativeAOT 15-30MB exe; cost is a full C# second stack and arms-length rclone integration (rcd sidecar or P/Invoke librclone). FINAL PICK for solo dev + rclone engine + Linux dev machine + Windows target + non-generic polish: WAILS. It collapses the architecture to one language and one process, eliminates the entire sidecar/IPC failure surface, cross-compiles with a single env var, and the web tier is where a solo dev can most cheaply achieve genuinely polished, virtualized, progress-heavy UI. Reserve Tauri as fallback if Wails v3 stalls AND v2 proves limiting; regardless of choice, budget a GitHub Actions windows-x64 runner for smoke tests, code signing, and optional MSIX. Known gap to design around in both webview options: drag-out of remote files to Explorer needs a small piece of custom native code.

## FINDINGS
CONTEXT: dual-pane file manager GUI (local+remote browse, virtualized lists, transfer queue with live progress, drag & drop, context menus, site manager), Windows x64 target, Linux (Ubuntu) dev machine, engine likely rclone (Go), solo/small team, must stay responsive under heavy background transfers. As of 2026-08.

CROSS-COMPILE FROM LINUX -> WINDOWS X64 (the decisive axis):
- Wails: BEST-IN-CLASS. Windows target needs NO CGO (WebView2 bound via pure-Go syscalls), so `GOOS=windows GOARCH=amd64` works from any host with zero extra setup; official v3 docs state Windows is the simplest cross-target. v2 stable = v2.12.0 (2026-03-26); v3 still alpha (v3.0.0-alpha2.114, 2026-07-05) but API "reasonably stable, production apps ship on it".
- Tauri 2.x: works via `cargo-xwin --target x86_64-pc-windows-msvc` + NSIS on Linux (documented, used in real GitLab/GitHub CI); officially "experimental" and cargo-xwin downloads Windows SDKs locally. MSI (WiX) still requires a Windows machine; NSIS installer cross-builds fine. Code signing cross-host is fiddly.
- Electron: electron-builder cross-builds Windows NSIS installers from Linux routinely (mature, years of practice). Easiest cross-build of the web trio after Wails.
- Avalonia: `dotnet publish -r win-x64 --self-contained` from Linux is fully supported first-class .NET behavior; NativeAOT to win-x64 from Linux also works (community-verified, 15-30MB single exe vs ~60-95MB self-contained JIT). Avalonia 12 preview (early 2026) ships a new composition renderer + perf gains.
- WPF: buildable on Linux only with EnableWindowsTargeting hacks; not designed for it; WinUI 3 effectively REQUIRES a Windows host (Windows App SDK, MSIX tooling). 2026 commentary treats WinUI 3 investment as risky/stagnating; WPF is maintained but 20-year-old tech.
- Flutter desktop: `flutter build windows` officially requires a Windows host + Visual Studio toolchain; no supported Linux->Windows cross-compile (long-standing open issue #106992). Must use Windows CI runners.
- Qt 6: cross-compiling via MXE/MinGW is possible but painful (toolchain builds up to ~10h, wine-vs-real-Windows discrepancies reported); MSVC-quality builds realistically need Windows CI. LGPL requires dynamic linking discipline; commercial license expensive for solo dev.
- egui/Slint (Rust): trivial cross-compile (windows-gnu via mingw or msvc via cargo-xwin), single static exe of a few MB.
- Compose Multiplatform: jpackage explicitly CANNOT cross-package — Windows MSI/EXE must be built on Windows (WiX dependency); JetBrains says cross-compilation is a non-goal. Conveyor (commercial for closed-source) is the workaround.

BINARY SIZE / MEMORY (2026 figures from comparisons):
- Electron: ~150-200MB installer, 150-200MB RAM empty, 300-500MB in production apps.
- Tauri: single-digit-to-low-double-digit MB bundle, ~45MB idle RAM (uses system WebView2, preinstalled on Win10 21H2+/Win11).
- Wails: similar profile to Tauri (~8-15MB exe, WebView2), plus rclone engine linked IN-PROCESS adds ~20-30MB to the exe but removes a separate process.
- Avalonia: 15-30MB (AOT) to ~95MB (self-contained), RAM ~80-150MB typical.
- egui/Slint: 5-20MB exe, lowest RAM.
- Flutter: ~25-60MB, moderate RAM; Compose: 60-150MB+ JVM bundle, JVM-class RAM.

VIRTUALIZED LISTS / PROGRESS-HEAVY UI:
- Web-frontend options (Wails/Tauri/Electron): solved problem — TanStack Virtual, react-virtuoso, AG Grid handle 100k+ row directories; progress bars/animations trivial; UI runs in a separate WebView2 process so heavy Go/Rust backend work cannot jank the UI thread by construction. This directly addresses the CuteFTP "can't browse while transferring" complaint.
- Avalonia: TreeDataGrid + built-in virtualization is genuinely excellent for file-manager UIs (flat + hierarchical, columns, sorting); arguably the best native-widget answer here.
- Flutter: ListView.builder virtualization is first-class; Qt: QListView/QTreeView model-view virtualization mature; egui show_rows works but immediate-mode repaints burn CPU/battery on idle-animated progress UIs (a 2026 benchmark of heavy tables across egui/iced/Slint/GTK found all Rust options strained vs Electron); Slint has ListView but complex multi-column file-manager tables are significant DIY; Compose LazyColumn fine.

WIN11 NATIVE LOOK & PACKAGING:
- None of the cross-buildable options is truly "native" (WinUI 3 is, but is Linux-hostile and risky). Web frontends can implement Fluent 2 convincingly (Fluent UI React components) and Mica-like styling; user wants "polished non-generic", which favors web-tier styling freedom per the anti-template design rules. Avalonia ships Fluent theme approximating Win11. MSIX packaging essentially requires Windows tooling/signing for every framework; NSIS/Inno installers are the pragmatic cross-built path (Tauri emits NSIS from Linux; Wails v3 has packaging tasks; electron-builder emits NSIS).

GO/RCLONE PAIRING:
- Wails: UNIQUE ADVANTAGE — backend IS Go. Import rclone as a library (librclone / fs packages) in-process: direct callbacks for progress events over Wails' event bus, no IPC serialization, no sidecar lifecycle management, single exe. This is the tightest possible coupling with the chosen engine.
- Tauri: sidecar pattern (externalBin) running `rclone rcd` + HTTP/WebSocket rc API on 127.0.0.1:5572. PROVEN: rclone-ui (github.com/rclone-ui/rclone-ui, active 2025-26, Tauri) and RClone Manager (Zarestia-Dev, Angular+Tauri, cross-platform incl. Windows) both ship this architecture today — strong prior art to study/fork per the research-first rule. Cost: two processes, port management, JSON-over-HTTP progress polling (rc core/stats), packaging the rclone.exe per-target-triple.
- Electron: same sidecar approach, well-trodden. Avalonia/.NET: sidecar rcd over HTTP, or c-shared librclone DLL via P/Invoke (works, but cross-compiling a c-shared Go DLL for Windows from Linux needs mingw-w64 CGO — doable, extra CI complexity). Flutter/Qt/Compose/egui/Slint: all sidecar-only, no affinity.

MATURITY 2026: Electron (dominant, 8k+ Mac App Store apps, boring-reliable); Tauri 2.x stable and the current default for new lightweight web-tech desktop apps; Wails v2 stable/maintained, v3 late-alpha with production users — plan for v2 now or accept alpha-tracking on v3; Avalonia very healthy (MIT, commercial backing, v12 preview); Qt mature but heavy/license-awkward for solo; Flutter desktop mature-ish but Windows-host-locked builds; WinUI 3 widely viewed as a risk; egui/Slint improving but under-powered for a polished dense file manager; Compose desktop functional but JVM + no cross-packaging.

RISK NOTES: (1) All WebView2 approaches share one weakness: native drag-OUT of virtual files to Explorer (CFSTR_FILEDESCRIPTOR) needs custom native code; drag-in and in-app DnD are fine. Tauri has community plugins (tauri-plugin-drag); Wails exposes native layer via Go + windows syscalls. (2) Wails v3 timing: if it hasn't gone stable by project start, v2 is fully viable (v2.12.0) with a documented v2->v3 migration path. (3) A Windows VM or GitHub Actions windows runner will still be needed for final smoke-testing and code signing regardless of framework.

## OPTIONS
- Wails (v2.12 stable / v3 alpha2) [MIT, v2 stable & maintained (v2.12.0, 2026-03); v3 late-alpha (alpha2.114, 2026-07), API stable-ish, production users, GA pending]: PROS: Backend IS Go: link rclone/librclone in-process, direct progress events, single exe, no sidecar/IPC; Best Linux->Windows cross-compile of all candidates: no CGO needed for Windows target, plain GOOS=windows works from any host; Small footprint: ~10-15MB exe + system WebView2, ~45-60MB RAM class; Web frontend => virtualized lists (TanStack Virtual), rich progress UI, full styling freedom for a non-generic Fluent-2 look; UI in WebView2 process is isolated from transfer engine by construction => responsive during heavy transfers CONS: v3 not GA — either ship on v2 or track alpha; v2->v3 migration later; Not native widgets; Win11 look must be recreated in CSS; Drag-out of files to Explorer requires custom native Go code; Smaller ecosystem than Electron/Tauri; NSIS installer, MSIX needs Windows tooling
- Tauri 2.x [MIT/Apache-2.0, Stable, very active, the 2026 default for lightweight web-tech desktop apps]: PROS: Proven rclone architecture: rclone-ui and RClone Manager both ship Tauri + rclone rcd sidecar today (forkable prior art); Cross-compiles Linux->Windows x64 via cargo-xwin + NSIS in CI (documented, working); Tiny bundles (sub-20MB), ~45MB idle RAM, system WebView2; Same web-frontend advantages as Wails for virtualized lists and progress UI; Biggest plugin ecosystem of the lightweight options (updater, deep-link, drag plugins) CONS: Rust core = second language next to Go; rclone must run as sidecar process with HTTP rc API (port mgmt, JSON polling, lifecycle); Linux->Windows cross-build officially 'experimental'; MSI/WiX still needs Windows; signing cross-host fiddly; Progress streaming via rc API polling is coarser than in-process callbacks
- Avalonia 11/12-preview (.NET 8/9) [MIT, Very healthy; v11 stable, v12 preview (new compositor) early 2026; commercial backing]: PROS: First-class Linux dev + `dotnet publish -r win-x64` cross-build; NativeAOT gives 15-30MB single exe; TreeDataGrid + built-in virtualization is the best native-widget fit for a dual-pane file manager; Real desktop widget toolkit: menus, DnD, accessibility more 'native' than webviews; Fluent theme approximates Win11; XAML/MVVM tooling mature; no webview dependency at all CONS: Go pairing is arms-length: rclone rcd sidecar over HTTP, or c-shared librclone P/Invoke (CGO mingw cross-build complexity); C#/.NET is a full second stack next to the Go engine; Fluent theme approximates but doesn't equal Win11 look; styling to 'non-generic polish' is more work than CSS
