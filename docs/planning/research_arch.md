## RECOMMENDATION
Build a custom Go transfer engine (option 3) rather than wrapping rclone as the SFTP engine. Architecture: (1) per-site SiteConnectionManager with one dedicated browse connection (never carries file data — this alone fixes the CuteFTP problem) plus a lazily-grown, jitter-ramped transfer connection pool (default cap 4) that auto-shrinks and requeues on "administratively prohibited"/refused errors from MaxSessions(10)/MaxStartups(10:30:60); (2) SQLite-WAL persistent queue-of-record with transactional state transitions, priorities, per-site caps, token-bucket global+per-site bandwidth limits, and two-level retry (op-level immediate, file-level exponential backoff + jitter); (3) transfer workers doing pipelined SFTP with 64–256 outstanding requests and negotiated chunk size up to 255k (fallback 32k), plus optional 2–4 offset-ranged streams per large file written into a preallocated destination (no merge step, avoiding Cyberduck's segment-assembly failure mode); (4) native SFTP resume: .part file + STAT size/mtime validation + offset reads — rclone fundamentally cannot resume partial files (restarts at byte 0; --inplace can even delete existing destination data on failure), and multi-threaded SFTP is still an open rclone issue (#8185), which disqualifies rclone as the core engine for this product's hard requirements; (5) GUI communicates over a push event stream (in-process channels if the GUI is Go/Wails; gRPC server-streaming or WebSocket-NDJSON on loopback with per-launch token if the GUI is a Tauri/Flutter/WinUI sidecar) — rclone rcd is poll-only with no interactive-prompt channel, so host-key TOFU dialogs and overwrite prompts are only cleanly possible with an owned engine; (6) Windows credential layer: Credential Manager/DPAPI for passwords and passphrases, agent-first key auth trying \\.\pipe\openssh-ssh-agent then Pageant fallback, per-site pinned host keys with a TOFU fingerprint dialog and a loud distinct changed-key alarm. Keep librclone as a LATER optional in-process plugin strictly for cloud backends (S3/GDrive), where rclone's semantics (no resume, poll stats) are acceptable. Go cross-compiles windows/amd64 from the Ubuntu dev box with zero extra toolchain, satisfying the cross-compilation constraint.

## FINDINGS
TOPIC 1 — BROWSE-WHILE-TRANSFERRING (how mature clients do it):
- WinSCP: for each background (queue) operation it opens a SEPARATE SSH connection using the same session options as the main session; finished connections are kept alive and reused for later queue items. Default = 2 simultaneous background operations (configurable in Preferences > Background). The main session stays free for browsing ONLY if the user routes transfers through the queue; foreground transfers block the panel — this is the exact failure the user experiences in CuteFTP. Key lesson: never share the browse channel with data transfer; make "queue by default" the only transfer path.
- FileZilla: every concurrent transfer opens a separate session; "max simultaneous transfers" EXCLUDES the browsing connection while "max simultaneous connections" includes it — i.e., a dedicated browse connection plus a transfer pool. Shared hosts commonly cap ~8 connections/IP; extras are rejected/queued.
- Cyberduck: since 4.7 uses multiple connections per transfer; segmented downloads (Preferences > Transfers) split files >100MB into parts over parallel connections and merge afterward (merge can be slow; GitHub issue #13374 documents segment-corruption edge cases — post-merge size/checksum validation is mandatory).
- rclone: SFTP backend keeps an internal pool of SSH connections (limit via --sftp-connections; idle-pool keepalive is still an open issue #9357). rclone historically ignores server-side session caps and just fails ("administratively prohibited" / connection refused) — the recommended mitigation is manual --transfers reduction. A robust client must auto-degrade instead.
- Server limits: OpenSSH MaxSessions (default 10) = max multiplexed sessions (sftp subsystem channels) PER TCP CONNECTION; MaxStartups (default 10:30:60) = concurrent UNAUTHENTICATED connections, probabilistically dropped between start and full. Two orthogonal strategies exist: (a) N separate TCP connections (FileZilla/WinSCP model — hits MaxStartups if opened in a burst, and per-IP caps), (b) one TCP connection with N multiplexed SFTP channels (hits MaxSessions=10 but only 1 auth handshake). Best practice: open connections lazily with staggered/jittered ramp-up, detect channel-open failure ("administratively prohibited") and connection-refused separately, and shrink the pool automatically with the failed transfer re-queued, not errored.

TOPIC 2 — QUEUE ENGINE:
- Persistence: FileZilla persists its queue in queue.sqlite3 and reloads on restart; corruption is the known failure mode (their trac #12900) — use SQLite WAL mode + write queue-item state transitions transactionally. WinSCP's queue is NOT persistent across restarts (a common complaint). rclone rcd jobs are in-memory only — daemon restart loses all jobs (jobid+executeId exist precisely because jobids reset per process). Therefore the QUEUE OF RECORD must live in our own store, never inside rclone.
- Resume: SFTP resume is protocol-native — SSH_FXP_READ/WRITE carry 64-bit byte offsets; client STATs the partial file, compares size+mtime, reopens and continues from offset. WinSCP implements this (.filepart + resume). rclone does NOT resume partial file transfers at all: interrupted files restart from byte 0 on the next run; --partial gives .partial temp files, --inplace writes directly to the final name and DELETES the file on failure (can destroy a pre-existing file). This is the single strongest argument against rclone-as-engine for large-file SFTP work.
- Multi-stream per file: rclone's --multi-thread-streams (default 4, cutoff 250M) does NOT apply to SFTP — issue #8185 (multi-threaded sftp, opened Nov 2024) is still open with no linked PR (checked 2026-08). WinSCP explicitly cannot split one file across connections (parallel = different files only). Cyberduck can (segmented). BUT: for SFTP the bigger win is single-connection request pipelining — protocol allows many outstanding READ/WRITE requests; rclone sftp exposes chunk_size (32k default per RFC; up to 255k works on OpenSSH, dramatic gains on high-latency links) and concurrency (outstanding requests per file, default 64). WinSCP defaults to 32×32KB=1MB in flight (SFTPDownloadQueue/SFTPUploadQueue raw settings). WinSCP's slowness causes per their own FAQ: latency × small windows, plus single-core encryption ceiling. A modern engine gets near-line-rate on one connection with 128–256 outstanding 128–255KB requests + aes-gcm/chacha20 (or splits one file across 2–4 connections when the server tolerates it, with offset-ranged reads into a preallocated sparse file — merge-free, unlike Cyberduck's segment files).
- Throttling/retry: rclone rc has core/bwlimit (dynamic, rate=up:down). Engine design: token-bucket shared per-site + global, applied in the read/write loop. Retry: per-file retries with exponential backoff + jitter; distinguish transient (net) from permanent (perm denied) errors; rclone's model is --low-level-retries (op level) + --retries (whole-job) — replicate both levels. Checksums: SFTP has no standard checksum op; check-support for md5sum/sha1sum only where server exposes shell commands (rclone probes this); otherwise verify size+mtime, and post-merge hash for multi-stream assemblies.

TOPIC 3 — GUI<->ENGINE COMMUNICATION:
- rclone rcd is POLLING-ONLY: _async=true returns jobid; GUI polls job/status and core/stats (optionally filtered by _group="job/N"); core/transferred holds last 100 completed. No WebSocket/SSE push exists in rclone as of 1.72.x (Dec 2025). All GUIs (RcloneView, rclone-ui, rclone-rc-web-gui) poll; smooth progress bars require ~250–500ms polling + client-side interpolation of bytes/speed. rcd security: loopback default :5572; rc access = shell access as the rclone user, so bind loopback + random port + per-launch generated user/pass; --rc-no-auth restricts to pre-configured remotes only.
- Alternative rclone embeddings: librclone (C shared library exposing the whole rc API in-process via RPC calls, sync and async) removes the HTTP hop and daemon-lifetime mismatch but keeps the poll-based stats model and the no-resume/no-multithread-SFTP semantics.
- Native-engine pattern: engine emits typed events (transfer-started, progress{bytes,rate,eta}, completed, failed, queue-changed, hostkey-prompt) over a push channel: same-process = channels/dispatcher; separate process = gRPC server-streaming or WebSocket/NDJSON on loopback. Push beats polling for: instant pause/cancel acknowledgment, hostkey/overwrite interactive prompts (rclone rc has NO interactive prompt callback — a hard problem for host-key UX through rcd), and no missed short-lived transfers between polls.

TOPIC 4 — WINDOWS STATE/CREDENTIALS:
- DPAPI (CryptProtectData / Win32 Credential Manager CredWrite with CRED_PERSIST_LOCAL_MACHINE|ENTERPRISE) is the standard for stored passwords; per-user master key derived from the Windows logon password. Windows OpenSSH ssh-agent stores DPAPI-protected keys in HKCU registry (ropnop's extraction research = why agent keys are preferable to app-managed key files). Caveat: passwordless logons (S4U/public-key SSH into the box) cannot unlock DPAPI — degrade gracefully to prompting.
- Agent interop on Windows: two ecosystems — Windows OpenSSH agent on named pipe \\.\pipe\openssh-ssh-agent (Win10 1809+/Server 2019+) and PuTTY Pageant (own protocol; modern Pageant also offers a named pipe). Bridges like WinCryptSSHAgent implement five protocols (Cygwin socket, AF_UNIX, named pipe, Pageant, Xagent). A CuteFTP/WinSCP replacement should speak BOTH: try openssh-ssh-agent pipe first, fall back to Pageant shared-memory protocol (WinSCP does exactly this).
- Host-key UX: TOFU with fingerprint dialog (SHA256 base64 + randomart), store per-site in app DB (not global known_hosts, but offer import FROM known_hosts/PuTTY registry), hard-fail with a distinct "KEY CHANGED" alarm dialog on mismatch, allow pre-pinning expected fingerprint in site config for scripted use. This must flow through the GUI event channel as a blocking prompt — impossible through rclone rcd, workable with librclone only by pre-answering (known_hosts file), natively trivial.

RECOMMENDED COMPONENT ARCHITECTURE (synthesis):
Single-process core with two logical layers, or GUI+engine split — either way the ENGINE is custom Go (cross-compiles to windows/amd64 trivially from Ubuntu, mature github.com/pkg/sftp + golang.org/x/crypto/ssh):
1. SiteConnectionManager (per site): one dedicated BROWSE connection (interactive ls/stat, low latency, never used for data) + a TRANSFER pool (lazy, jittered ramp-up, cap default 4, auto-shrink on channel-open failure/MaxStartups drop; failed transfer requeued). Avoids: CuteFTP's frozen browsing, rclone's hard failure on server caps, MaxStartups burst drops.
2. QueueEngine: SQLite (WAL) queue-of-record; states pending/active/paused/failed/done; per-site concurrency caps; priorities; token-bucket global+per-site bwlimit; two-level retry (op-level + file-level exp backoff+jitter). Survives crash/restart (rclone rcd cannot; WinSCP queue cannot). Resume via native SFTP offset semantics into .part files with size+mtime validation (rclone cannot). Optional 2–4 offset-ranged streams per large file into preallocated file when server allows (no merge step, unlike Cyberduck).
3. Transfer workers: goroutine per active transfer; within a file, pipelined async READ/WRITE with 64–256 outstanding requests, negotiable chunk up to 255k on tolerant servers, fallback to 32k on errors (rclone/WinSCP tuning evidence).
4. Event bus to GUI: typed push events (progress at ~10Hz coalesced, prompts as blocking request/response). If GUI is a separate process (e.g., Tauri/Flutter/WinUI shell + Go sidecar): gRPC server-streaming or WebSocket NDJSON on loopback with per-launch token. Avoids: polling lag, missed events, rcd's no-interactive-prompt gap, rcd's shell-equivalent attack surface.
5. CredentialStore: Windows Credential Manager (DPAPI) for passwords/passphrases; keys preferentially via agent (openssh pipe → Pageant fallback); per-site pinned host keys with TOFU dialog + changed-key alarm.
6. Optional rclone integration LATER as a pluggable backend (librclone in-process) strictly for cloud remotes (S3/GDrive) where rclone excels — NOT as the SFTP engine, because of: no partial-file resume, no multi-thread SFTP (open issue #8185), poll-only progress, in-memory jobs, no interactive prompts.

## OPTIONS
- rclone rcd subprocess as transfer engine (GUI polls HTTP rc API) [MIT, rclone 1.72.1 stable (Dec 2025); rc API stable and used by RcloneView/rclone-ui in production]: PROS: 70+ storage backends for free (S3, GDrive, Azure, plus SFTP/FTP); _async jobs, _group-scoped core/stats, core/bwlimit dynamic throttling already built; Battle-tested transfer loop, retries (--retries/--low-level-retries), bwlimit schedules; Go binary cross-compiles/ships trivially for Windows x64; several shipped GUIs prove the pattern CONS: NO partial-file resume: interrupted files restart at byte 0; --inplace can delete pre-existing destination on failure; NO multi-thread SFTP per file (issue #8185 open since Nov 2024, no PR as of Aug 2026); Poll-only progress (no WebSocket/SSE); jobs are in-memory — daemon restart loses queue (jobid resets per process); No interactive prompt channel: host-key TOFU dialogs, overwrite prompts impossible through rcd; rc access = shell-equivalent; needs careful loopback+auth hardening; Ignores server session caps — fails hard instead of degrading when MaxSessions/MaxStartups hit
- librclone embedded in-process (rc API via C shared lib / gomobile) [MIT, Stable, used by rclone's own mobile apps]: PROS: Same backend breadth without HTTP daemon, port, or auth surface; Process lifetime matches app; no orphaned daemon; Callable from Go natively or any language via cgo/FFI CONS: Inherits all rclone semantics: no SFTP resume, no per-file multi-stream SFTP, poll-based stats, no prompt callbacks; FFI complexity if GUI language is not Go; Still need own persistent queue on top
- Custom Go engine (pkg/sftp + x/crypto/ssh) with SQLite queue + push event bus [with optional librclone plugin later for cloud backends] [BSD (both libs), pkg/sftp and x/crypto/ssh are mature, widely deployed (rclone itself uses them); engine logic is new code]: PROS: Native SFTP resume via protocol offsets (SSH_FXP_READ/WRITE 64-bit offsets + STAT size/mtime validation) — the thing rclone can't do; Full control of connection topology: dedicated browse connection + jittered lazy transfer pool + auto-shrink on MaxSessions/MaxStartups failures; Per-file parallelism both ways: pipelining (64–256 outstanding requests, chunk up to 255k) AND optional offset-ranged multi-connection streams into preallocated file (no merge step); Push progress events (channels/gRPC stream) → smooth bars, instant pause/cancel, blocking host-key/overwrite prompts; SQLite WAL queue-of-record survives crash/restart (FileZilla-proven pattern, avoiding their corruption bugs via transactional state transitions); Go cross-compiles windows/amd64 from Ubuntu with zero toolchain pain; single static engine binary CONS: Most new code to write and test (transfer loop, retry ladder, throttling); SFTP-family only at first; cloud backends require the later librclone plugin; Must implement own checksum verification strategy (SFTP has no standard hash op; probe for md5sum/sha1sum like rclone does)
- Native C++/Rust engine (libssh2 / russh+rust-sftp) or C# SSH.NET in a WinUI app [BSD/MIT/Apache mix, libssh2 mature; russh maturing; SSH.NET mature but single-lang lock-in]: PROS: Same architectural freedoms as custom Go engine; Rust/C++ can squeeze more per-core crypto throughput; C# integrates directly with WinUI/DPAPI APIs CONS: Cross-compilation from Ubuntu to Windows x64 is materially harder than Go (MSVC/mingw toolchains, or Rust windows-gnu target quirks); SSH.NET resume support is a known gap (issue #1391); libssh2 async model is callback-heavy; Smaller ecosystem overlap with rclone-style cloud backends if scope grows
- WinSCP .NET assembly / winscp.com automation as backend [GPL (assembly wrapper restrictions apply), Very mature product (WinSCP 6.x)]: PROS: Proven SFTP stack with resume (.filepart), background-connection reuse pattern to copy; Handles Pageant + openssh-agent + PuTTY key formats already CONS: Cannot split one file across connections (explicitly unsupported); GPL licensing constrains a proprietary product; Automation surface is session-scripted, not an event-streaming engine; queue not persistent; Windows-only dev/test loop conflicts with Linux dev machine
