# WINNER: DESIGN B — Performance-First Go/Wails client (custom SFTP fast path + in-process rclone)

## RATIONALE
B wins because it dominates exactly the criteria the product exists for. "Blazingly fast" is priority #1, and the two speed gaps that matter (multi-connection-per-file SFTP, byte-level resume) are ones rclone structurally cannot close (issue #8185 open since Nov 2024 with no PR; research_arch calls no-resume "the single strongest argument against rclone-as-engine"). Design A's own Phase 3 is the confession: fastsftp.exe is Design B's engine rebuilt in miniature, in a third language, bolted onto a Tauri app via JSON-over-stdout, creating two engines with divergent pause/resume/progress semantics. If that custom Go SFTP code must exist either way, B's architecture puts it in the primary process and primary language from the start. B also wins the fact-check fights: its browse-while-transfer guarantee is structural (dedicated browse connection + WebView2 isolation) where A's is a heuristic over a pool rclone doesn't let you reserve; its pause/resume is protocol-native where A's restarts files at byte 0 through v1; and its cross-compile story (pure Go, CGO off) is strictly stronger than A's officially-experimental cargo-xwin. Three of five dossiers converge on B's shape — research_gui's final pick is Wails, research_arch's recommended architecture is nearly a spec for B, research_workspace pre-scaffolds go-wails-app and identifies Go as the user's stated stack — which also blunts B's biggest weakness: the solo-dev tarpit risk of a custom engine is materially lower for a Go-fluent dev than A's four Rust modules inside an unfamiliar Rust/TS fork. B's honest downgrades (rclone-backed sites labeled "file-level resume", no --inplace, Wails v2 not v3 alpha) survive adversarial checking; its only inflated claims are schedule estimates, and a late MVP that is right beats an early MVP that caps out at rclone's ceiling. One correction to carry forward: B's assertion that host-key TOFU is "impossible" without an owned engine is overstated — A's pre-flight keyscan proves pre-answering works — but that only removes an argument for B, not B's advantage.

## GRAFTS
1) Port rclone-ui's Apache-2.0 React navigator suite (Commander.tsx, FilePanel, FileList, PathBreadcrumb, react-resizable-panels layout) into the Wails frontend instead of "stealing patterns, not code" — both stacks are React+TS; adapting these components against B's ipc.ts attacks B's single biggest schedule risk (greenfield dual-pane UI) and could claw back 2–3 weeks. 2) A's pre-flight keyscan discipline for anything rclone executes: whenever a transfer runs through librclone against an SSH-family backend, inject known_hosts_file pointing at an app-owned file populated by B's own probe — never rclone's no-check default — and scan ALL server key types so strict checking can't false-fail on algorithm mismatch. 3) A's pre-dispatch conflict resolution (stat destination while the item is still pending, apply site policy) as the default path, keeping B's blocking overwrite prompts only for races discovered mid-transfer — fewer stalled workers. 4) A's rc-endpoint smoke suite for engine upgrades: pin rclone and gate every go.mod bump on a test pass over the exact RPC surface rcadapter uses. 5) A's progress interpolation (rAF lerp + EMA speed) on the frontend for RcloneStatsPoller-driven transfers, where B inherits rclone's 300ms poll granularity. 6) Pull A's S3/MinIO-first instinct forward: librclone S3 is near-zero marginal code and is the fastest secure path when the user controls the server — ship it at the end of Phase 1 rather than deep in Phase 2. 7) A's explicit 2-week timebox-then-fallback rule, applied to B's SiteConnectionManager and chunked mode individually (B's ">2 weeks slips get demoted" rule, made per-component and calendar-bound).

## DISSENT
The strongest honest case for Design A: it is the only plan where a daily-drivable CuteFTP replacement provably exists in ~6-8 weeks, because every genuinely hard, unglamorous subsystem — dual-pane browse UI, rc job tracking, sidecar lifecycle, Linux→Windows packaging, winget distribution — is inherited from a shipping v3.7.1 app rather than written, and research_oss verified those pieces in the source tree rather than assuming them. Its speed 'deficit' is largely theoretical for the common case: 128 outstanding requests × 255K chunks ≈ 32 MB in flight saturates 1 Gbps out to ~250 ms RTT on a single connection, so unless the user routinely moves >1 GiB single files over high-RTT or lossy links, tuned rclone is already 'blazingly fast' and B's custom engine buys nothing observable while costing months of correctness work (resume validation, chunk checkpointing, connection-cap edge cases, SSH security handling) that rclone's enormous test matrix and 58k-star community currently absorb for free. A's TOFU solution survives adversarial review intact — the rcd 'no prompts' objection is fully neutralized by pre-flight keyscan + strict known_hosts — and its riskiest bet (cargo-xwin) has working prior art in the fork's own CI. Design A wins under any of these conditions: the dev's real-world Rust/TS fluency exceeds their Go fluency (contrary to the workspace dossier's inference); target links are ≤1 Gbps at moderate RTT so the SFTP ceiling is never hit; calendar time to replacing CuteFTP is the true KPI rather than peak throughput; rclone merges #8185 or byte-resume within the next year (instantly stranding B's engine investment); or the solo dev judges lifetime ownership of a security-sensitive custom SSH transfer engine to be a heavier liability than a fork divergence and a poll-based progress bar.
