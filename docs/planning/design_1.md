# FileBeam — Performance-First Go/Wails File-Transfer Client (custom SFTP fast path + in-process rclone)

## SUMMARY
FileBeam is a single-process Windows x64 desktop app at ~/DevProjects/filebeam/ built on Wails v2 (stable v2.13), where the Go backend IS the transfer engine — no sidecar, no IPC serialization, no polling gap. Two engines share one SQLite-WAL persistent queue: (1) a custom SFTP fast path on github.com/pkg/sftp + x/crypto/ssh delivering pipelined 64–256 outstanding requests with up-to-255K chunks, optional mscp-style multi-connection chunked transfers into a preallocated .part file (merge-free), true byte-level pause/resume, a dedicated browse connection per site (the structural fix for CuteFTP's frozen-panel flaw), and blocking host-key TOFU prompts over the Wails event bus; (2) rclone v1.75 imported as a Go library (librclone.RPC, identical surface to rcd but in-process) providing FTP/FTPS, S3, WebDAV and 70+ backends with _async jobs mapped into the same queue. React+TypeScript frontend with TanStack Virtual dual-pane lists renders in WebView2's own process, so UI responsiveness under load is guaranteed by construction. Everything cross-compiles Ubuntu→windows/amd64 with CGO off (modernc.org/sqlite, danieljoos/wincred, go-winio are all pure Go); CI does lint/test/cross-build on Linux and signing (Azure Trusted Signing) + NSIS + smoke tests on a windows-latest runner. MVP in ~6–8 weeks ships a faster-than-WinSCP SFTP client; v1 adds the rclone backends and the multi-connection fast path.

## PROCESS & THREAD MODEL

ONE OS process pair, both managed by Wails v2:
- **filebeam.exe (Go)** — Wails runtime + ALL engine logic. No sidecar, no daemon, no localhost port, no rc auth surface. This is the decisive advantage of the Wails path per research_gui: the backend IS Go, so rclone is a package import and the SFTP engine shares memory with the UI bridge.
- **WebView2 renderer** — spawned/managed by Wails; the React UI runs in Microsoft's separate renderer process. Heavy engine work physically cannot jank the UI thread. Combined with the dedicated browse connection (below), "browse while transfers run" is guaranteed at BOTH layers: process isolation for rendering, connection isolation for protocol.

**Wails v2.13 (stable), not v3 alpha — justification:** v2 is stable/maintained (v2.13.0 Jul 2026), its Windows target needs NO CGO (WebView2 via pure-Go syscalls), and Linux→Windows cross-compile is community-verified (discussion #2632, metal3d/wails-cross-compile). v3 (alpha2.114) has nicer packaging tasks but is still alpha with doc/tooling churn — wrong risk for a solo dev's core framework. Mitigation for the eventual v2→v3 migration: all frontend↔backend traffic goes through two thin Go interfaces (`Bindings` facade + `EventSink`) and one TS module (`ipc.ts`); only those files touch `wailsapp/wails/v2/pkg/runtime`. Migration is then a contained diff, and Tauri+rcd sidecar remains a documented escape hatch (rclone-ui proves it).

Goroutine topology inside filebeam.exe:
- **QueueDispatcher** (1): pulls `pending` rows, enforces global + per-site concurrency caps, routes each item to NativeSFTPEngine or RcloneAdapter by the item's `engine` column.
- **SiteConnectionManager** (per open site): owns 1 dedicated browse `*sftp.Client` + a lazily-grown transfer pool.
- **Transfer workers**: one goroutine per active transfer; N sub-goroutines per chunked transfer (one per connection).
- **EventCoalescer** (1): batches progress into ≤10 Hz per transfer before EventsEmit — keeps the JS bridge cheap even with 50 active transfers.
- **RcloneStatsPoller** (1, only while rclone jobs exist): polls `core/stats` with `_group=job/N` at 300 ms and converts to the same typed events, so the frontend never knows which engine ran a transfer.
- **PromptBroker** (1): turns Go-side blocking questions (host key, overwrite, FTPS cert) into request/response over the event bus.

## ENGINE SPLIT — HONEST BOUNDARY

**Custom native engine: SFTP only.** Research_arch disqualifies rclone as the SFTP core for this product's hard requirements: no byte-level resume (restarts at byte 0; --inplace can destroy destination data on failure), no multi-connection-per-file SFTP (issue #8185 open since Nov 2024, no PR), poll-only progress, no interactive prompt channel (host-key TOFU impossible), in-memory jobs. The native engine exists precisely to fill those five gaps, and pkg/sftp is the same library rclone itself uses, so we're not betting on exotic code.

**rclone-as-library: everything else.** FTP/FTPS (with --ftp-concurrency), S3 (multipart + --multi-thread-streams — the genuinely fastest secure path when the user controls the remote, per research_engine; a "MinIO profile" site type exposes it), WebDAV, SMB, and the other 70+ backends. Import `github.com/rclone/rclone/librclone/librclone` directly (pure Go — since the GUI is Go there is NO cgo, no DLL, no mingw; research_engine explicitly blesses direct import for Go GUIs). Call `librclone.RPC("sync/copy", json)` etc. — identical surface to rcd, so swapping to a subprocess rcd later (crash isolation, independent upgrades) is a contained change inside rcadapter. Endpoints used: `operations/list` (remote browse for rclone-backed sites), `operations/copyfile`/`sync/copy`/`operations/deletefile`/`operations/mkdir` with `_async=true` + `_group`, `job/status`, `job/stop`, `core/stats`, `core/bwlimit` (live rate changes), `config/create`/`config/update`. Remote definitions are injected via rclone's config API from our own store — we implement rclone's config storage interface backed by SQLite + Credential Manager so rclone secrets never hit disk plaintext.

**No custom FTP engine** (scope discipline): rclone's FTP backend is adequate; FTP byte-resume via REST is a possible v1.x native addition, not MVP/v1.

## HOW EACH HARD REQUIREMENT IS MET

**1. Blazingly fast transfers.**
- SFTP throughput = outstanding_requests × chunk_size / RTT (research_engine). Native path: pkg/sftp with `UseConcurrentReads/Writes(true)`, `MaxConcurrentRequestsPerFile` 64 default, adaptive up to 256; chunk size starts 32 KiB, probes up to ~255 KiB on tolerant servers (OpenSSH 256 KB packet ceiling), falls back on failure. 256×255K ≈ 64 MB in flight — saturates 1 Gbps at high RTT on ONE connection, versus WinSCP's default 32×32KB=1MB window (their own documented slowness cause).
- Cipher preference order aes128-gcm@openssh.com, chacha20-poly1305, aes128-ctr (AES-NI GCM = multi-Gbps single core).
- Multi-connection chunked mode (v1, mscp model, proven against stock sshd): files > cutoff (default 128 MiB, configurable) split into offset ranges across 2–4 pooled connections, each writing/reading its range directly into a **preallocated destination .part** — merge-free, avoiding Cyberduck's segment-assembly corruption mode; post-transfer size + (where server exposes md5sum/sha1sum, probed rclone-style) hash validation.
- Parallel files: dispatcher runs up to per-site cap (default 4) + global cap concurrently.
- rclone-backed backends: `--transfers`, `--multi-thread-streams 4–8` for S3/HTTP (ranged reads supported there), `--ftp-concurrency` for FTP — passed per-job via `_config`.

**2. Browse while transfers run.** Per-site dedicated browse connection that NEVER carries file data (the FileZilla/WinSCP lesson distilled in research_arch), owned by SiteConnectionManager; transfer pool is separate connections. Listings stream to the UI as typed events; rendering is in WebView2's own process. All three historical failure layers (shared connection, blocking UI thread, foreground transfer path) are eliminated — there is no non-queue transfer path at all: every transfer goes through the queue by design.

**3. Persistent queue.** SQLite in WAL mode (modernc.org/sqlite, pure Go — keeps CGO_ENABLED=0) at %APPDATA%\FileBeam\filebeam.db. Tables: `sites`, `transfers(id, site_id, engine, direction, src, dst, size, state, priority, bytes_done, attempt, next_retry_at, error, rclone_jobid, created_at, updated_at)`, `chunks(transfer_id, idx, offset, length, bytes_done, state)`, `hostkeys(site_id, algo, sha256_fp, pinned_at)`, `settings`. State machine: `pending → dispatched → active → completed | paused | failed | cancelled`; `failed → retry_wait → pending` (file-level exponential backoff + jitter; op-level immediate retries inside workers — rclone's two-level model replicated). Every transition is a single transaction (FileZilla's queue.sqlite3 corruption lesson). On startup, `dispatched/active` rows are demoted to `pending` (crash recovery); rclone jobids are per-process and never trusted across restarts — the SQLite queue, not rclone, is the queue of record.

**4. Pause/resume.** Native SFTP: pause = stop issuing requests, drain in-flight, fsync .part, record bytes_done (+ per-chunk offsets for chunked mode), state `paused` — instant, byte-accurate. Resume = STAT .part, validate size + remote mtime/size unchanged, reopen at offset (SSH_FXP_READ/WRITE carry 64-bit offsets — protocol-native). Chunked transfers resume per-chunk from the `chunks` table (mscp-style checkpointing). rclone-backed items: honest downgrade, surfaced in the UI as "file-level resume" — pause = `job/stop` + requeue; on resume the job re-runs with size/modtime skip semantics so completed files aren't re-sent, but an interrupted file restarts. `--partial` set, `--inplace` NEVER set (destination-deletion hazard).

**5. Host-key UX.** ssh.ClientConfig HostKeyCallback checks the per-site pin in `hostkeys`. Unknown key → PromptBroker emits `prompt:hostkey` (SHA256 base64 fingerprint + randomart) over the Wails event bus and blocks the connecting goroutine on a channel; frontend modal answers via bound `ResolvePrompt(id, answer)`; timeout = deny. Accept pins the key. Mismatch → hard fail + loud, visually distinct "HOST KEY CHANGED" alarm dialog (never a routine confirm). Importers for OpenSSH known_hosts and PuTTY's registry keys at site creation. This blocking-prompt flow is exactly what rcd cannot do and a core reason the SFTP engine is owned. FTPS (rclone-backed): self-signed certs get a one-time TOFU pin captured via our own tls.Dial probe at site-add; the pinned cert is passed to rclone via the remote's CA config rather than no_check_certificate.

**6. Credentials on Windows.** Passwords/key-passphrases → Windows Credential Manager via danieljoos/wincred (DPAPI-backed, per-user); `sites` rows hold only a credential reference. Key auth is agent-first: dial `\\.\pipe\openssh-ssh-agent` (Microsoft/go-winio + x/crypto/ssh/agent), fall back to Pageant's protocol (davidmz/go-pageant) — the WinSCP dual-agent pattern. App-managed key files are last resort, passphrase in wincred. Graceful degradation to prompting when DPAPI is unavailable (passwordless logon caveat). All of creds/ sits behind an interface with in-memory fakes so the Linux dev loop and tests run without Windows.

**7. Solo-dev Linux→Windows story.** Entire binary builds with `CGO_ENABLED=0 GOOS=windows GOARCH=amd64` from the Ubuntu box (Wails Windows target needs no CGO; rclone, modernc sqlite, wincred, winio, go-pageant all pure Go). Dev loop: `wails dev` on Linux (native Linux build of the same code; Windows-only paths behind build tags + fakes). NSIS installer built on Linux (`apt install nsis`). GitHub Actions: job 1 (ubuntu-latest): golangci-lint, go test ./..., frontend vitest, cross-build filebeam.exe + NSIS; job 2 (windows-latest): install artifact, launch + WebView2 smoke test (Playwright against the Wails window's debug endpoint), sign via azure/trusted-signing-action (Azure Trusted/Artifact Signing, ~$10/mo, Windows-runner-only), attach signed NSIS to release. Optional local Win11 eval VM (quickemu) for interactive debugging only. Later Linux/macOS ports are cheap: same Wails codebase; creds/ swaps to libsecret/Keychain implementations behind the existing interface; macOS build needs a mac runner.

## SITECONNECTIONMANAGER (the anti-CuteFTP/anti-rclone-hard-fail component)
Per site: browse connection opened eagerly on site open; transfer pool grown lazily one connection at a time with 250–750 ms jitter between dials (avoids MaxStartups 10:30:60 probabilistic drops on bursts). Error classifier separates: channel-open "administratively prohibited" (MaxSessions ceiling on that TCP conn → try a new TCP connection or shrink), TCP refused / handshake drop (MaxStartups or per-IP cap → shrink pool cap, requeue the transfer — never error it), auth failures (permanent → surface). Pool cap auto-shrinks on repeated rejections with backoff before re-growth; per-site max-connections is user-settable (shared hosts commonly cap ~8/IP). Keepalive pings on idle pooled connections; idle connections beyond a floor are reaped.

## EVENT CONTRACT (Go → JS via Wails EventsEmit)
`transfer:progress {id, bytes, rate, eta}` (coalesced ≤10 Hz), `transfer:state {id, state, error?}`, `queue:changed`, `listing:chunk {panelId, entries[]}`, `prompt:hostkey|overwrite|ftpscert {promptId, payload}` (blocking, resolved by bound method), `site:connstate`, `engine:bwlimit`. JS → Go via generated Wails bindings: Enqueue, PauseTransfer, ResumeTransfer, CancelTransfer, Reorder, List, Mkdir, Delete, Rename, ResolvePrompt, SetBandwidthLimit (token bucket for native engine; core/bwlimit for rclone jobs), site/cred CRUD.

## RISKS
- [HIGH] Custom SFTP engine scope balloon — chunked multi-connection transfers, resume correctness, and connection-pool edge cases are the classic solo-dev tarpit; this is the steel-man's weak point since rclone-only would ship sooner at lower peak speed. -> MVP ships single-connection pipelined only — which already beats WinSCP's 1MB in-flight window by 16-64x and saturates 1 Gbps at moderate RTT (research_engine math). Chunked mode is Phase 2, feature-flagged, mscp's proven design (offset ranges, per-chunk checkpoints, stock-sshd compatible). Property-based tests on the resume/offset logic + testcontainers sshd matrix (MaxSessions/MaxStartups/chunk-size variants) from Phase 1. Hard rule: any fast-path feature slipping >2 weeks gets demoted to the rclone path for that release.
- [HIGH] Windows fidelity gap from an all-Linux dev loop: wincred/DPAPI, agent pipes, WebView2 quirks, SmartScreen reputation, and signing can only be truly validated on Windows. -> windows-latest CI job from Phase 0 (install + launch + Playwright smoke + signed artifact every merge); creds/ and agent code behind interfaces with fakes so logic is unit-tested on Linux; Azure Trusted Signing from the first public build (best SmartScreen story without EV tokens); local Win11 eval VM (quickemu) reserved for interactive debugging of pipe/DPAPI behavior.
- [MEDIUM] Wails framework risk: v2→v3 migration cost later, and v2's Linux→Windows cross-compile being community-verified rather than officially blessed. -> All Wails API usage confined to the Bindings facade + EventSink + frontend ipc.ts (three files); CI cross-builds and smoke-tests the Windows exe on every merge so a toolchain regression is caught same-day; v3's own docs make Windows the easiest target, so migration improves this axis; documented fallback is Tauri 2 + rclone rcd sidecar (rclone-ui prior art), which reuses the entire React frontend and the queue/engine Go code behind a gRPC stream.
- [MEDIUM] rclone-as-library coupling: ~25-30MB binary growth, large dependency tree pinning Go version expectations, and rclone's semantics (no byte resume, poll-only stats, no prompts) leaking into UX for rclone-backed sites. -> Pin rclone at a tested tag and upgrade deliberately per release; rcadapter is the only package importing rclone, and librclone.RPC's surface is identical to rcd's HTTP API, so swapping to a subprocess rcd (crash isolation, independent engine upgrades) is a contained change; UI explicitly labels rclone-backed transfers 'file-level resume' and never sets --inplace (destination-deletion hazard documented in research_arch); host-key/cert trust for rclone backends is established by our own pre-flight probe, never delegated to rclone prompts that don't exist.
- [MEDIUM] Server-side connection caps (OpenSSH MaxSessions=10, MaxStartups=10:30:60, shared-host ~8-conn/IP limits) causing hard transfer failures or bans — the failure mode rclone handles by failing and FileZilla by user tuning. -> SiteConnectionManager is designed around this: lazy jittered ramp-up (no bursts into MaxStartups), separate classification of channel-open 'administratively prohibited' vs TCP-refused, automatic pool shrink with requeue (never user-visible error), backoff before regrowth, user-settable per-site cap defaulting to 4; browse connection is always reserved so browsing survives even a pool collapse; integration tests run against sshd containers configured with hostile caps.
